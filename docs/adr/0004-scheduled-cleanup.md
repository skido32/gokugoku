# 0004: 保持期間を過ぎたデータは、外からの定期実行で消す

> 状態: 採用 / 日付: 2026-11-28
> 変えるもの: design.md 4.10「削除は記録するときに行う」

## 決定
- 保持期間を過ぎたデータと不要になった認証情報は、rake タスク `bin/rails maintenance:cleanup` で消す。
  - 対象は、90日を過ぎた授乳記録、論理削除から24時間を過ぎた記録、失効したセッション、使用済み・期限切れのコード、放置された利用者(家族なし・30日未使用)。
- 1日1回、**GitHub Actions の定期実行**から、Fly.io の一時的なマシンでこのタスクを動かす。設定は、本番のデプロイ(週3)で、DB のバックアップと同じワークフローに入れる。
- ジョブ基盤(Solid Queue など)は入れない。
- 授乳記録を作るときの、その家族の古い記録の削除は残す(二重の守り)。

## 理由
- **記録するときに消す方式だけでは、保持期間を守れない。** 記録をやめた家族(子どもが大きくなった家族)の記録は、書き込みが起きないため残り続ける。この使われ方で最も多い場面で、方針が守れなくなる。
- **認証なしの API から、全体の掃除を動かさない。** 当初、利用者の作成(`POST /v1/accounts`)で放置された利用者を消していた。誰でも呼べるリクエストが、件数に上限のない、他人のデータの削除を動かす形になり、失敗すると初回起動も失敗する。
- **増える負担が小さい。** バックアップ(`pg_dump`)を GitHub Actions で取ると決めているため、DB の接続先を外から使うこと、DB を1日1回起こすことは、どちらにしても発生する。Neon の無料プラン(月 100 CU時間、5分で停止)に対し、1日5分なら月 0.6 CU時間ほど。
- **消す条件を Rails の中に置き、テストできる。** SQL を外に書く方式では、条件が二重になり、テストできない。

## 検討した他の案
| 案 | 採らなかった理由 |
|---|---|
| 書き込みのときに、件数の上限つきで消す | 記録をやめた家族のデータが残る問題が解決しない |
| GitHub Actions から `psql` で SQL を流す | 条件が Rails の外に二重になり、テストできない |
| Fly.io の定期実行のマシン | 間隔が粗い(毎時・毎日など)。終了後に再起動を繰り返す報告がある |
| Solid Queue の定期実行 | 常に DB へ問い合わせ、Neon の停止を妨げる(design.md 4.10) |

## 受け入れる弱点と対策
| 弱点 | 対策 |
|---|---|
| 公開リポジトリでは、60日活動がないと定期実行が止まり、通知もない | 最後に成功した日時を監視する(週3の監視の設定で行う)。止まっても、データが残るだけで壊れない |
| 実行時刻が数分〜数時間ずれる | 掃除なので問題にしない |
| Fly.io のトークンを GitHub に置く | そのアプリ専用のデプロイ用トークンにし、Environment `production` で main からだけ使えるようにする。fork からの PR には渡らない |
| 本番のデプロイまで、掃除が動かない | 本番がまだないため、問題にならない |

## 見直す条件
- 非同期の処理が、掃除以外にも必要になった場合 → ジョブ基盤を検討する。
