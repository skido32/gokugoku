# 0003: 登録なしの匿名アカウントにする(メールを持たない)

> 状態: 採用 / 日付: 2026-11-22
> 置き換えるもの: メールの6桁コードによるログイン(当初の F-AUTH-1〜5)

## 決定
- **初回の起動で、利用者を自動で作る。** メール、パスワード、電話番号は入力させない。
- 端末は、サーバーが発行したトークンを Keychain(iOS)/ Keystore(Android)に保存し、`Authorization: Bearer` で API を呼ぶ。
- 夫婦の共有は、**招待コード**(リンクでも開ける)で行う。
- 機種変更・端末の紛失には、**引き継ぎコード**で備える。
- メールアドレスは、MVP では一切持たない。メールの登録は、必要になったら、任意の引き継ぎ手段として後から足す。

## 理由
- **初回の操作を最小にする。** 最も近い競合のミルクのーとは、登録もログインもない。「開いてすぐ記録できる」体験で、並ぶ必要がある。
- **個人情報をさらに減らす。** メールアドレスを持たなければ、漏えいしても、利用者を特定する情報がほぼない。子どもの情報を最小限しか扱わない方針と一致する。
- **作るものと、外部依存を減らす。** メール送信のサービス、`login_codes` テーブル、メールの回数制限、送信失敗の扱いが要らなくなる。
- ストア審査のプライバシー申告が簡単になる。

## 受け入れる弱点と対策
| 弱点 | 対策 |
|---|---|
| 端末を失うと、その利用者には戻れない | 夫婦の両方が使っていれば、残った端末から招待し直せる(データは家族に残る)。1人だけの家族は、引き継ぎコードを事前に発行しておく必要がある。初回ガイドで、パートナーの招待を勧める |
| トークンを盗まれると、なりすまされる | トークンは推測できない長さ(256ビット)にし、サーバーにはハッシュだけを保存する。設定から失効できる。端末の安全な保管場所にだけ保存する |
| 利用者を無制限に作られる | 作成を IP ごとに回数制限する。必要になれば App Attest / Play Integrity を検討する |
| 招待コード・引き継ぎコードの推測 | 推測されにくい長さ、有効期限、1回限り、試行の回数制限。サーバーには HMAC だけを保存する |
| 使われなくなった匿名の利用者が残る | 長期間使われていない家族の扱いは、未決事項として残す |

## 見直す条件
- 端末の紛失で、データを失った家族が出た場合 → メールの登録(任意)を足す。
- 不正な大量作成が起きた場合 → 端末の検証(App Attest / Play Integrity)を足す。
